皆様、こんにちは。Configuration Manager / WSUS サポート チームです。

本記事では、Configuration Manager (Current Branch) の自動展開規則 (ADR) が実行されたときに、サイト側で何が処理され、設定によって結果がどう変わるかを説明します。設定手順と実際のログを使った追跡例は、[自動展開規則についての動作説明](https://jpmem.github.io/blog/mecm/20260916_01/) をご覧ください。本記事ではログ抜粋を掲載せず、各工程で確認する結果とログの用途を紹介します。クライアント側はサイト側との境界までを扱います。

## 全体の流れ

1. 規則の評価を開始する
2. フィルター条件に一致する更新プログラムを選ぶ
3. ソフトウェア更新プログラム グループにまとめる
4. 設定に応じてコンテンツを取得・配布する
5. グループを対象コレクションに展開する

この順序は、規則の評価から展開までに確認する結果を整理したもので、内部処理やログの記録順を示すものではありません。たとえば、関連記事では、Microsoft Defender Antivirus の定義更新プログラムを対象とする ADR を展開パッケージありで手動実行し、グループの処理より先にコンテンツの取得が記録された例を紹介しています。

## 各ステップとログの追跡方法

### 関連ログ

| ログ名 | 保存場所 | 主な用途 |
| --- | --- | --- |
| ruleengine.log | サイト サーバーの Configuration Manager インストール フォルダー配下の `Logs` | 規則の評価、更新プログラムの選定、コンテンツの取得、およびグループと展開の処理を確認します。 |
| PatchDownloader.log | ADR では、サイト サーバーに Configuration Manager クライアントがインストールされている場合、そのサーバーの `%windir%\CCM\Logs` | 更新元からのコンテンツ取得の詳細を確認します。 |
| distmgr.log | サイト サーバーの Configuration Manager インストール フォルダー配下の `Logs` | 展開パッケージの処理や、配布ポイントへのコンテンツ配布要求を確認します。 |
| PkgXferMgr.log | サイト サーバーの Configuration Manager インストール フォルダー配下の `Logs` | サイト サーバーからリモートの配布ポイントへのコンテンツ転送を確認します。 |
| PolicyAgent.log | 対象クライアントのログ フォルダー (既定は `%windir%\CCM\Logs`) | クライアントによるポリシーの取得を確認します。 |
| UpdatesDeployment.log | 対象クライアントのログ フォルダー (既定は `%windir%\CCM\Logs`) | クライアント側での展開の評価や適用の進行状況を確認します。 |

ログ ファイル リファレンスでは、サイト サーバーにクライアントがインストールされていない場合の ADR の PatchDownloader.log 保存先は明示されていません。コンソールの実行ユーザーの `%TEMP%` に記録されるのは、コンソールから更新プログラムを手動でダウンロードする場合です。ADR をコンソールから手動で起動する場合とは異なります。

### ステップ 1 : 規則の評価を開始する

ADR が有効であれば、ソフトウェア更新ポイント (SUP) の同期後、指定スケジュール、または管理者による手動操作を契機に規則を評価します。自動実行を設定しない場合も、手動で評価を開始できます。SUP の同期は更新プログラムのメタデータを取り込む処理であり、更新ファイルをダウンロードする処理とは別です。

規則が実行されたかどうかは、想定した時刻の ruleengine.log で対象の規則の評価を確認します。評価が見当たらない場合は、規則自体が有効かどうかと、設定した実行契機を満たしたかどうかを分けて確認します。

### ステップ 2 : フィルター条件に一致する更新プログラムを選ぶ

サイトは、同期済みの更新プログラムから、製品、分類、リリース日または改訂日など、規則に設定された条件に一致するものを選びます。ADR の上限は、コンテンツ ファイル数ではなく、更新プログラム 1,000 件です。

候補がない場合や件数が想定と異なる場合は、まず ruleengine.log で評価対象の規則と選定結果を確認します。そのうえで、対象の更新プログラムのメタデータが同期済みか、規則の条件に一致するかを確認すると、取得や展開の処理に進む前の段階を切り分けられます。

### ステップ 3 : ソフトウェア更新プログラム グループにまとめる

選定した更新プログラムを新しいグループにまとめる構成では、実行ごとにグループを作成します。既存のグループを使う構成では、グループ内の更新プログラムをいったんすべて外し、今回選定した更新プログラムで入れ替えます。以前の実行で追加された更新プログラムも、今回の条件に一致しなければグループには残りません。グループから更新プログラムを外す処理と、展開パッケージからコンテンツを削除する処理は別です。

想定したグループに反映されていない場合は、ruleengine.log で選定結果とグループの処理を確認し、コンソールでグループの新規作成または再利用の設定と、実際のメンバーを照らし合わせます。

### ステップ 4 : 設定に応じてコンテンツを取得・配布する

| 展開パッケージの構成 | サイト側で想定される結果 |
| --- | --- |
| 展開パッケージを使う | サイトは必要に応じてコンテンツを取得し、指定した配布ポイントに配布します。 |
| 展開パッケージを使わない | ADR はこの展開のためにコンテンツを事前取得したり、配布ポイントに配布したりしません。クライアントは Microsoft Update や、必要なコンテンツを保持するピアなどから取得できます。 |

[旧バージョンの展開追跡 KB](https://learn.microsoft.com/en-us/troubleshoot/mem/configmgr/update-management/track-software-update-deployment-process#create-a-deployment-by-using-an-automatic-deployment-rule) では、指定した展開パッケージにすでにあるコンテンツの再取得を省略する例を確認できます。この例は System Center 2012 / 2012 R2 Configuration Manager を対象としており、Current Branch のログの記録順やメッセージを示すものではありません。

取得の有無を確認するときは、まずパッケージの設定と ruleengine.log を確認します。取得が必要な場合の詳細は PatchDownloader.log、取得後の配布要求は distmgr.log、リモートの配布ポイントへの転送は PkgXferMgr.log で確認します。サイトが取得を終えたことと、配布ポイントでコンテンツが利用可能になったことは別なので、配布の完了は対象の配布ポイントのコンテンツの状態で確認します。

### ステップ 5 : グループを対象コレクションに展開する

サイトは、グループを対象コレクションに展開します。1 つの ADR に複数の展開を関連付けられるため、同じグループでも、対象コレクション、利用可能時刻、期限などを展開ごとに変えられます。

規則自体が有効で、展開だけが無効な場合、その展開からはクライアントに更新プログラムを展開しません。ただし、展開パッケージを使う構成では、展開が無効でも、規則の実行時に必要に応じてコンテンツが取得・配布されます。

サイト側では、ruleengine.log の展開処理と、対象グループに関連付けられた展開の対象コレクションおよび有効・無効を確認します。

ADR の処理完了と、対象クライアントでのインストール完了は別です。有効な展開のポリシーを受け取ったクライアントが、適用対象を評価し、必要なコンテンツを取得して、展開の設定に従ってインストールします。クライアント側では、ポリシーの取得は PolicyAgent.log、展開の評価や適用の進行状況は UpdatesDeployment.log で確認します。
