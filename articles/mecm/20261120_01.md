皆様、こんにちは。Configuration Manager / WSUS サポート チームです。

本記事では、Configuration Manager のクラウド管理ゲートウェイ (CMG) を作成するときに、Configuration Manager と Azure で行われる処理、およびログの確認方法をご案内します。

仮想マシン スケール セットを使用する CMG を対象に、作成ウィザードでの構成指定から Azure への展開、オンプレミスとの接続確認までを説明します。証明書の発行手順、既存 CMG の移行、およびクライアントのインストール手順は対象外です。

本記事は Microsoft の公開資料を基に説明しており、実ログの抜粋や、実ログによる工程間の対応付けは掲載していません。

## 全体の流れ

1. 作成ウィザードで CMG の構成を指定する
2. サービス接続ポイントが Azure へ CMG を展開する
3. Azure 上で CMG のセットアップを行い、サービスが準備完了になる
4. CMG 接続ポイントを構成し、オンプレミスから CMG への接続を確立する
5. 接続アナライザーで CMG 経由の通信を確認する

作成処理を理解するうえでは、次の 2 つのサイト システムの役割を区別すると、確認する箇所を整理しやすくなります。

| 役割 | CMG に関する主な処理 |
| --- | --- |
| サービス接続ポイント | クラウド サービス マネージャー コンポーネントを実行し、Azure への CMG の展開と監視を行います。 |
| CMG 接続ポイント | オンプレミスから CMG に接続し、CMG が受信したクライアント要求を管理ポイントなどへ中継します。 |

これらの役割と通信方向は、[CMG の計画](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/plan-cloud-management-gateway)および [CMG のデータ フロー](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/data-flow)に記載されています。

## 動作説明の前提

Configuration Manager current branch で、仮想マシン スケール セットとして新規作成する構成を対象とします。バージョン 2203 以降では、新規 CMG の展開方法は仮想マシン スケール セットのみです。

作成前には、展開先の Azure サブスクリプションと必要なリソース プロバイダー、Configuration Manager と Microsoft Entra ID の統合、および CMG のサーバー認証証明書を準備します。サービス接続ポイントはオンライン モードとし、サービス接続ポイントと CMG 接続ポイントのそれぞれから必要な宛先に通信できるようにします。

ウィザードで Azure にサインインする管理者の権限と、作成要求を受けてサイト側が展開を実行するための構成は別です。具体的な権限や通信先は、[CMG の計画](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/plan-cloud-management-gateway)と [CMG のデータ フロー](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/data-flow)をご確認ください。

## 各ステップとログの追跡方法

### 関連ログ

| ログ名 | 保存場所・確認先 | 主な用途 |
| --- | --- | --- |
| CloudMgr.log | CMG を管理する最上位サイト (中央管理サイトまたはプライマリ サイト) のサイト サーバーの Configuration Manager インストール先の Logs フォルダー | CMG の展開処理、サービスの状態、および使用状況を確認します。 |
| CMGSetup.log | Azure 上で生成され、CMG を管理する最上位サイトのサイト サーバーの Logs フォルダーに同期されます。 | Azure 内で行われる CMG 展開の第 2 段階のセットアップを確認します。 |
| CMGService.log | Azure 上で生成され、CMG を管理する最上位サイトのサイト サーバーの Logs フォルダーに同期されます。 | CMG サービスの稼働状況とクライアント要求の処理を確認します。 |
| SMS_Cloud_ProxyConnector.log | CMG 接続ポイントをホストするサイト システム サーバー上。実際のログ保存先は、そのサーバーのインストール構成に合わせて確認します。 | CMG への接続と、CMG とオンプレミスの間の要求の中継を確認します。 |

CMGSetup.log と CMGService.log の実際のファイル名には、サービス名とロール インスタンスの識別子が含まれます。CloudMgr.log から確認を始めるときは、コンソールで選択した CMG の名前、展開先のリソース グループ、ウィザードを完了した時刻を控えておくと、Azure の展開履歴や同期されたログから同じ作成操作に絞り込めます。複数のインスタンスがある場合は、CMG 側のログをインスタンスごとに確認します。

CMG 側のログは 5 分ごとに Azure ストレージへ送信され、クラウド サービス マネージャーが 5 分ごとに同期するため、同期が正常な場合でもローカルへの反映には最大 10 分の遅延があります。作成直後に CMGSetup.log が見当たらない場合は、ログがまだ届いていない可能性と、セットアップまで処理が進んでいない可能性を区別するため、CloudMgr.log と Azure 側の展開履歴を先に確認します。ログ取得のために CMG へリモート デスクトップ接続する方法はサポートされていません。

ログの用途と同期の仕組みは、[CMG の監視](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/monitor-clients-cloud-management-gateway)のログを監視するセクションをご参照ください。

### ステップ 1 : 作成ウィザードで CMG の構成を指定する

管理者が Configuration Manager コンソールの [管理] - [クラウド サービス] - [クラウド管理ゲートウェイ] から作成ウィザードを開始します。

ウィザードでは、Azure 環境とサブスクリプションを選択し、展開リージョン、リソース グループ、および仮想マシンのサイズとインスタンス数を指定します。Azure 環境はグローバル Azure などの接続先を指し、リージョンはその環境内で CMG を展開する場所を指します。既存のリソース グループを使用する場合は、CMG と同じリージョンのグループを選択します。

サーバー認証証明書の .pfx ファイルを指定すると、証明書の共通名を基に [サービス名] と [展開名] が入力されます。サービス名はクライアントと CMG 接続ポイントが接続に使う名前です。展開名は、Configuration Manager がサービス名の先頭部分と展開リージョンを基に組み立てる Azure ドメイン上の名前です。ワイルドカード証明書を使う場合は、[サービス名] のアスタリスク (*) を Azure で一意の展開名の先頭部分に置き換えます。

独自ドメインの名前をサービス名に使う場合は、公開のドメイン ネーム システム (DNS) で、サービス名を別名として Azure の展開名に対応付ける正規名 (CNAME) レコードを構成します。これにより、クライアントは証明書に対応するサービス名で接続しながら、接続先のアドレスを解決できます。Azure の展開名自体をサービス名に使う構成では、このレコードは不要です。詳細は [CMG の設定](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/setup-cloud-management-gateway)と [CMG のサーバー認証証明書](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/server-auth-cert)をご参照ください。

ウィザードの完了は、ここで指定した内容によるセットアップの開始点です。ウィザード内で進めない場合は、その画面のエラーに沿って Azure へのサインイン、対象サブスクリプションの権限、証明書などの入力を確認します。ウィザードが完了した場合は、コンソールで対象 CMG の状態を確認し、CloudMgr.log でサイト側の展開処理を追います。

### ステップ 2 : サービス接続ポイントが Azure へ CMG を展開する

サービス接続ポイントで実行されるクラウド サービス マネージャーは、Microsoft Entra ID を使用して認証し、Azure Resource Manager (ARM) 経由で指定されたリソース グループに CMG を展開します。この通信は、オンプレミスのサービス接続ポイントから Azure への HTTPS (ポート 443) の送信接続です。後述の CMG 接続ポイントによる CMG への接続とは、接続先も目的も異なります。

Azure 側には、CMG の仮想マシン インスタンスを実行する仮想マシン スケール セットや、CMG の運用に使われる Azure ストレージ アカウントなどが展開されます。ストレージ アカウントは CMG 側のログ同期にも使われます。そのため、ストレージ アカウントが作成されていることだけでは、仮想マシン上で CMG が起動したことや、クライアントにコンテンツを配信できることまでは確認できません。

CloudMgr.log でサイト側の展開処理を確認し、Azure portal では対象リソース グループの [デプロイ] から [展開履歴](https://learn.microsoft.com/ja-jp/azure/azure-resource-manager/templates/deployment-history)を確認します。Azure 側で失敗した操作がある場合は、その操作のエラー詳細を CloudMgr.log と照合します。Azure 側で対象の展開を確認できない場合は、まずサブスクリプションとリソース グループが合っているかを確認し、CloudMgr.log に記録された処理に応じて、サービス接続ポイントの通信や認証、必要な権限やリソース プロバイダーの登録状況を確認します。

### ステップ 3 : Azure 上で CMG のセットアップを行い、サービスが準備完了になる

Azure リソースの作成に加え、Azure 内では仮想マシン上で CMG サービスがセットアップされます。CMG は、指定されたサーバー認証証明書を使って HTTPS サービスを構成します。Azure 側に仮想マシン スケール セットが表示されても、CMG サービスのセットアップが終わったとは限りません。

ARM の展開履歴では、リソース グループへの展開と、そこで実行された操作の結果を確認できます。一方、スケール セットの各インスタンスの[プロビジョニング状態](https://learn.microsoft.com/ja-jp/azure/virtual-machines/states-billing#provisioning-states)は、その仮想マシンに対する Azure 側の作成や更新などの処理状態を示します。これらが成功していても、Configuration Manager が CMG の準備完了を確認したことにはなりません。

サービスの準備は、Configuration Manager コンソールで対象 CMG の状態が [準備完了] になったことを確認します。状態が進まない場合は、CloudMgr.log でサイト側が把握している展開状態を確認し、Azure 側の状態と照合します。CMGSetup.log が同期されていれば、仮想マシン上で行われた CMG サービスのセットアップも確認します。

この時点で確認できるのは CMG サービスの準備です。クライアント要求をオンプレミスへ中継するためには、次の CMG 接続ポイントなどの構成も必要です。

### ステップ 4 : CMG 接続ポイントを構成し、オンプレミスから CMG への接続を確立する

管理者がサイト システム サーバーに CMG 接続ポイントの役割を追加し、接続先の CMG を選択します。また、利用する管理ポイントやソフトウェア更新ポイントで CMG トラフィックを許可します。管理ポイントを HTTPS 用に構成するか、サイトで拡張 HTTP を有効にする必要があります。詳細は、[CMG の計画](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/plan-cloud-management-gateway)および [CMG の設定](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/setup-cloud-management-gateway)をご参照ください。

CMG 接続ポイントは、オンプレミスから Azure 上の CMG へ接続を開始し、接続情報やセキュリティ設定を CMG に公開します。CMG が受信したクライアント要求は、この確立済みの接続を通じて CMG 接続ポイントへ転送され、オンプレミスのサイト システムへ中継されます。このため、CMG がオンプレミスへ新規の受信接続を開始する必要はありません。

仮想マシン スケール セット構成では、CMG 接続ポイントから CMG への接続に HTTPS を使用します。CMG の仮想マシンが 1 台の場合はポート 443 を使用します。2 台以上の場合は、443 ではなく、1 台目に 10124、2 台目に 10125 と、インスタンスごとに異なるポートを使用します (16 台目は 10139)。ポートを決めるのは CMG 側の仮想マシンの台数であり、CMG 接続ポイントの数ではありません。インターネット上のクライアントから CMG への HTTPS 接続は、仮想マシンの台数にかかわらずポート 443 を使用します。詳しくは [CMG のデータ フロー](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/data-flow)をご参照ください。

この段階では SMS_Cloud_ProxyConnector.log で CMG 接続ポイント側の接続状況を確認し、CMGService.log で Azure 側のサービスの稼働状況を確認します。CMG が [準備完了] でも接続を確立できない場合は、先に接続先 CMG の設定、CMG 接続ポイント上でのサービス名の名前解決、CMG への送信に必要なポート、ログに記録された証明書関連のエラーを確認します。接続が確立していても要求が管理ポイントまで届かない場合は、接続そのものではなく、転送先のサイト システムの設定と通信を確認します。

### ステップ 5 : 接続アナライザーで CMG 経由の通信を確認する

CMG サービスと接続ポイントを構成した後は、コンソールで対象 CMG を選択して [接続アナライザー] を開きます。確認したい認証方法に合わせて、[Microsoft Entra ユーザー] を選択してユーザー アカウントでサインインするか、[クライアント証明書] を選択してクライアント認証証明書を使います。選択した条件で、CMG サービスの稼働状況と、CMG 接続ポイントを経由して CMG トラフィックを許可する管理ポイントまで通信できるかを確認します。操作の詳細は、[CMG の監視](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/monitor-clients-cloud-management-gateway)をご参照ください。

失敗した項目がある場合は、項目を選択して説明を確認します。たとえば、次のように結果に応じて調べる場所を切り替えます。

| 確認結果 | 次に確認する箇所 |
| --- | --- |
| サインインまたは証明書の指定でエラーになる | エラーの説明を確認し、選択した認証方法に応じて、使用する Microsoft Entra ユーザー アカウントまたはクライアント認証証明書を確認します。 |
| CMG が準備完了でない | ステップ 2 と 3 に戻り、CloudMgr.log、Azure の展開履歴、同期済みの CMGSetup.log を確認します。 |
| サービスの実行状態や構成に問題がある | テスト結果の説明と、CloudMgr.log や CMGService.log に記録されたサービスの状態を照合します。 |
| CMG 接続ポイントの接続に問題がある | ステップ 4 の経路を対象に、SMS_Cloud_ProxyConnector.log と CMGService.log を確認します。 |
| サイト システムや管理ポイントへの通信に問題がある | 対象の管理ポイントでの CMG トラフィックの許可、HTTPS または拡張 HTTP の構成、および CMG 接続ポイントからの中継を確認します。 |

CMG の [準備完了] はサービスの展開状態を示します。一方、接続アナライザーで確認できるのは、選択した認証方式での実行時点の通信です。すべての項目に成功しても、対象クライアントが CMG の場所情報を取得したことや、ソフトウェア更新ポイントへの通信やコンテンツの取得ができることまでは示しません。実際に利用する機能は、対象クライアントから別途ご確認ください。クライアント側の準備は [CMG 用にクライアントを構成する](https://learn.microsoft.com/ja-jp/intune/configmgr/core/clients/manage/cmg/configure-clients)をご参照ください。

作成後の継続的な監視については、関連記事の [クラウド管理ゲートウェイ (CMG) の監視と運用](https://jpmem.github.io/blog/mecm/20220522_01/)もご活用ください。
